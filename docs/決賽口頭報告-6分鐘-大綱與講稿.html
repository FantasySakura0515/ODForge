二、逐頁講稿

P1 封面（0:00–0:15）

各位評審好，我們是學生組的王巧晰、江慶于。我們的作品是 ODForge，中文名「文鍛」——把一句話，鍛造成一份正式的 ODF 文件。

P2 動機（0:15–0:45）

ODF 其實不缺地位：2006 年成為國際標準，2009 年納入國家標準，今天更是政府公文交換的標準格式。但在這波 AI 浪潮裡，支援 ODP 輸出的主流 AI 文件工具，是零個。大家不是不想用 ODF，是用起來比較累。所以我們把力氣花在一件事：讓 ODF 變省力。

P3 問題（0:45–1:20）

動手之前，我們把現有的路都親手走過一遍。AI 文件工具像 Gamma，只出 PPTX；Copilot 產的 PPTX 拆開來看，其實是 HTML 轉檔；PPTX 轉 ODP 會跑版，字級、母片、公式全壞；LibreOffice 的 AI 擴充，只能改寫選取的文字。也就是說，「一句話變一份原生 ODF」這條路，是空的。為什麼空了這麼多年？因為轉檔看似堪用、實則有損；Python 函式庫斷層；AI 生態根本不認識 ODF。

P4 目的（1:20–1:40）

所以我們的目的很單純：把 ODF 變成方便好用的 AI 工具。讓一句自然語言，變成一份合規、可以繼續編輯的原生 ODF。

P5 方法（1:40–2:25）★ 核心頁，放慢

方法上，我們把分工切得很乾淨：內容 AI 寫，格式引擎保證。直接叫 AI 吐檔案，是每次擲一次骰子；ODForge 把骰子換成機器。AI 只產出結構化 JSON，經過 schema 嚴格驗證；真正寫檔的，是我們自己開發的確定性渲染引擎，直接寫出 OpenDocument XML。我們還特別處理中文：ODF 的中文字級要另外設定 asian 屬性，只設一般字級，中文會掉回預設字級——多數工具沒處理，我們在引擎層強制寫對。每份檔案出廠前都過三道驗證：ZIP 結構、XML 正確性、LibreOffice 實際開檔。

P6 成果（2:25–2:55）

成果就是：一行指令，一份檔案。一套引擎，三種格式——.odt 文書、.odp 簡報、.ods 試算表，而且試算表是原生公式，開檔就會自動計算。包括各位眼前這份決賽簡報，也是 ODForge 生成的原生 .odp——直接補上 AI 簡報生成長年的空缺。

P7 使用體驗（2:55–3:20）

使用體驗上，我們不賭一把。Web 控制台會先問清楚、再開始寫：你用一句話描述需求，可以上傳講義或論文當取材；AI 針對缺少的資訊逐題追問——對象、頁數、重點、語氣——整理成一份可編輯的摘要，你點頭之後，它才動筆。

P8 生態貢獻（3:20–3:55）

更關鍵的是生態貢獻：ODForge 同時是一個 MCP server。任何 AI 助理——Claude、Cursor、Cline——一行設定掛上，就能直接產 ODF：不用改任何程式、不需要任何 API 金鑰，五個工具，涵蓋三種格式的生成，外加驗證與預覽。與其等 AI 生態想起 ODF，不如把 ODF 的出口，直接做進 AI 工具鏈。

P9 優化建議 1/2（3:55–4:35）★ 配分 30% 從這裡開始，口氣轉正式

接下來是我們對 ODF 生態的兩點優化建議，都是開發中親身踩到的。第一，Python 的 ODF 函式庫斷層：最知名的 odfpy，從 2020 年就停止更新，只支援 ODF 1.2；還在維護的 odfdo，簡報母片和版面的支援，連官方文件都承認陽春。結果就是：想做 ODF 工具的人，都得從零開始研究，我們的簡報渲染器最後只能全部手寫 XML。我們建議由官方或社群，維護一個有長期承諾的 ODF 參考實作；ODForge 的渲染引擎以 MIT 開源，可以直接作為這個起點。

P10 優化建議 2/2（4:35–5:10）

第二，AI 工具鏈裡沒有 ODF——等下去也不會有：開源簡報工具的 ODP 匯出請求，掛了好幾年沒人理。但反過來看，原生、可編輯、符合標準，正是 ODF 現在最大的優勢。我們建議推廣單位主動出擊：用 MCP server、編輯器外掛、對開源工具發 PR，把 ODF 的出口做進 AI 工具鏈——我們的 MCP server，已經示範這條路走得通。

P11 心得與推廣（5:10–5:40）

做完這個專案，最大的心得是：最有效的推廣不是講道理，是把路修平。對學生，一行指令，報告直接就是合規的 ODF；對老師，教材、簡報、成績表直出；對機關，省下文件撰寫的時間；對社群，全案 MIT 開源，歡迎接手。

P12 結語（5:40–6:00）

ODF 不缺標準，缺的是一條讓人願意走的路——我們把這條路修出來了。三種格式、五個 MCP 工具、零 API 金鑰。ODForge，把一句話，鍛造成一份正式文件。謝謝大家，歡迎現場出題實測。

定位與比較

Q5｜和政府推的 ODF 文件應用工具（或 LibreOffice）有什麼不同？會不會重複？

完全互補。那些是「編輯器」，我們是「生成引擎」——我們明確不做線上編輯器，產出的檔案就是要用 LibreOffice 或 ODF 文件應用工具打開繼續改。我們補的是它們前面那一段：從一句話到第一版檔案。

Q6｜直接叫 ChatGPT 寫 ODF 的 XML，不行嗎？

試過，那是每次擲一次骰子：XML 可能壞、中文字級會掉、座標會亂。在 ODForge 裡，LLM 從頭到尾不碰 XML、不碰公分與 pt，只寫結構化內容；版面座標全部由確定性引擎計算，同樣輸入永遠得到同樣版面。

Q7｜為什麼簡報渲染器要全部手寫 XML，不用現成函式庫？

不是不想用，是沒得用——odfpy 停更、odfdo 的母片與版面支援連官方文件都承認陽春。這正是我們優化建議第一點的親身證據。

Q8｜不會用終端機的老師、行政人員怎麼用？

兩條路：Web 控制台（瀏覽器操作、逐題訪談、確認後生成），或者在他們已經在用的 AI 助理裡掛上 MCP，用聊天的方式產檔。CLI 只是給進階使用者的第三條路。

Q9｜為什麼 Web 介面只支援簡報，不支援文書和試算表？

刻意的產品決定，不是沒做完。控制台的核心體驗是「一頁＝一個可預覽、可單獨重生的單位」，簡報有這個天然單位，文書和試算表沒有；後兩者由 CLI 和 MCP 完整支援。

AI 品質與內容正確性

Q10｜AI 會亂編內容（幻覺），你們怎麼處理？

誠實切分保證範圍：引擎保證「格式正確、打得開、版面看過」，內容真偽不在保證範圍，文件內明確標示「來源（未查證）」提醒使用者查證。流程上用兩道人工把關降低風險：生成前 AI 先追問確認需求、生成前先給可編輯大綱，人點頭才動筆。

Q11｜文字太多塞不下、跑版怎麼辦？

引擎內建版面預算檢查：用確定性的文字高度估算，逐頁逐框比對可用空間，超載時會指名「第幾頁哪個框、預估幾公分超過幾公分」。原則是「ODForge 量測，呼叫端重寫」——回報精確位置，讓 AI 或使用者針對性刪改，而不是偷偷縮字級破壞版面規範。

Q12｜生成的檔案怎麼證明符合標準？

三道閘門之外，最實際的證明是第三道：headless LibreOffice 真的開檔、真的轉出 PDF；試算表還會強制重算公式、掃描錯誤值。另外 odforge check 可以驗任何 ODF 檔——包括不是我們產的，歡迎評審拿檔案來測。

Q13｜中文處理到底特別在哪？

ODF 規範裡 CJK 文字的字級、粗體要另外設定 asian 系列屬性；只設一般屬性，中文會掉回預設字級。多數工具沒處理，我們在渲染層強制三軌齊備，這是寫進引擎的規則，不是用提示詞拜託 AI。

資安與部署

Q14｜上傳的講義、公文會不會外流？可以完全離線嗎？

可以。LLM 後端可插拔，接本機 Ollama 就全程資料不出門；MCP 模式更是連金鑰都沒有，內容由呼叫端的 AI 寫，ODForge 只做本機渲染。Web 控制台預設只綁本機 127.0.0.1。

Q15｜為什麼 MCP 模式不需要 API 金鑰？

因為 MCP server 是純渲染引擎，刻意不含任何 LLM 呼叫——內容是掛上來的那個 AI 助理自己寫的，ODForge 負責把它變成合規檔案並驗證。所以零金鑰、零外連。

Q16｜處理外部檔案安全嗎？

有做防護：XML 解析器硬化（防 XXE、實體炸彈）、ZIP 有界讀取（防解壓縮炸彈）、上傳檔案大小與數量上限。專案跑過安全稽核，未修復發現為零。

工程品質

Q17｜兩個學生做的，品質可信嗎？測試怎麼做？

產品碼約 1.6 萬行，測試碼約 1.4 萬行，接近一比一；分支覆蓋率 87.87%，門檻 85% 寫死在設定檔，低於就擋下。CI 有八條管線，涵蓋兩個 Python 版本、兩個作業系統，還有真的裝 LibreOffice 開檔的整合測試。

Q18｜開發中學到最重要的一課？

「測試全綠不等於做完。」我們做過對抗式複審：在測試全綠的基線上又找出二十多項可重現缺陷——包括乾淨環境安裝第一行就會 crash 的問題，因為開發機的舊套件把它遮住了。綠燈量的是「跑過的東西」，不是「該跑的東西」。

推廣與永續

Q19｜比賽結束後，這個專案會不會就停了？

全案 MIT 開源在 GitHub，文件、測試、CI 齊備，任何人都能接手；渲染引擎本身就能作為 Python ODF 參考實作的起點——這正是我們優化建議想促成的事。

Q20｜如果教育部或 ODF 推廣單位想採用，第一步建議做什麼？

成本最低、槓桿最大的一步：把 MCP server 這條路推廣出去。一行設定，就讓師生已經在用的 AI 助理直接產出合規 ODF——不用教新工具，在他們原本的工作流裡把出口換成 ODF。

Q21｜既有的舊檔案（docx）有幫助嗎？

有。odforge check 支援 docx 轉 odt 的前後結構比對，自動偵測轉檔跑版的位置，輸出報告——這是給「手上有一堆舊格式檔案」的機關的遷移輔助。

Q22｜學校的公版、機關的範本能用嗎？

可以。範本抽取功能能從既有的 .otp／.odt 公版抽出設計規格（色彩、字型、版面），之後生成的檔案就長在自己單位的公版上；也有範本庫可以存自訂組合。

需要團隊自行補答（我無法代答）

Q24｜生成一份簡報實際要多久？ ——渲染本身是毫秒級，時間主要花在 LLM 產內容，依後端而異；建議賽前用現場要 demo 的後端實測一次，記下「約 X 分鐘產一份 12 頁簡報」的實數。
