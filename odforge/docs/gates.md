# 品質閘定義（唯一權威來源）

> CLI、MCP、Web 控制台、README 與所有報告一律以本文件的詞彙為準。
> 任何一處與本文件不符，是那一處的錯。

這份文件存在的原因很直接：同一件事以前有四種說法。README 寫「每一份產出都必須
通過三道驗證閘」，Web 介面在第四格畫一個綠勾，CLI 在同樣的情況印「設計 OK」，而
實際上那一輪視覺評審根本沒有執行。這不是措辭問題——它讓使用者相信一件沒有發生
過的事。

---

## 一、四道閘各自保證什麼（以及**不**保證什麼）

| # | 名稱 | 保證 | **不**保證 | 需要 |
| --- | ------ | ------ | ----------- | ------ |
| 01 | 封裝結構 zip | ODF 套件結構合法：`mimetype` 為第一個且未壓縮的 entry、副檔名與 mimetype 相符、manifest 列出的部件都存在 | 內容是否正確、是否好看 | 無 |
| 02 | 內容格式 xml | 套件內每一個 `.xml` 部件都 well-formed，必要部件非空 | 是否符合 ODF **語意**（本專案不做 RELAX NG schema 驗證） | 無 |
| 03 | 實際開檔 libreoffice | LibreOffice headless 真的開得起來並轉出 PDF；`.ods` 另外強制計算並檢查是否出現 `#NAME?`、`#VALUE!`、`Err:` 等公式錯誤值 | 版面美不美、內容對不對 | LibreOffice |
| 04 | 設計品質 design | 視覺模型逐頁看過算圖後的影像，針對溢出、重疊、對比、對齊、版型節奏提出 findings，並對 `severity=error` 的頁面重生一輪 | **內容是否屬實**、來源是否存在、數字是否正確 | LibreOffice + 視覺模型 |

**四道閘全部通過，意思是：這是一份格式正確、LibreOffice 打得開、版面經過視覺
審閱的簡報。它不代表裡面寫的內容是真的。** 見第四節。

## 二、閘門狀態詞彙（六種，語意互不重疊）

| 狀態 | 顯示 | 意思 |
| ------ | ------ | ------ |
| `pending` | · 待處理 | 還沒輪到這一道 |
| `active` | ⟳ 進行中 | 正在跑 |
| `pass` | ✓ 已通過 | 跑完了，通過 |
| `fail` | ✕ 未通過 | 跑完了，沒通過 |
| `skipped` | — 未啟用 | **沒有人要求**跑這一道（使用者關掉 QA、或這次生成選擇不用視覺模型）。沒有問題，是刻意不做 |
| `unknown` | ? 無法判定 | **要求了，但跑不成**（沒有 LibreOffice、視覺來源拒絕、回應讀不懂）。這份交付的該項品質**實際上沒有被驗證過** |

`skipped` 與 `unknown` 長得不能一樣，這是整套詞彙的重點：前者是使用者的選擇，
後者是一個未被發現的品質缺口。**無法檢查不等於通過。**

## 三、閘門是阻斷閘還是觀察訊號？（定案）

| 閘 | 性質 | 依據 |
| ---- | ------ | ------ |
| 01 zip | **阻斷** | 失敗即中止流程，Web 不提供下載，CLI exit code 1 |
| 02 xml | **阻斷** | 同上 |
| 03 libreoffice | **觀察訊號** | 失敗或未安裝不中止交付。理由：LibreOffice 是外部相依，它的缺席或版本問題不代表產物有錯；但結果會如實顯示為 `fail` / `skipped` |
| 04 design | **觀察訊號** | 失敗不中止交付。理由：視覺評審是主觀判斷，且視覺模型可能配額用盡或回應不可解析；但結果會如實顯示為 `fail` / `unknown`，且**絕不**在沒跑的情況下顯示 `pass` |

因此正確的產品說法是：

> **每一份產出都必須通過封裝結構與內容格式兩道阻斷閘才會交付；LibreOffice 開檔
> 與設計品質兩道閘的結果一律如實回報，不會被略過也不會被美化。**

不要再寫「每一份都必須通過三／四道閘才會交付」——那句話與程式行為不符。

## 四、「格式可信」與「內容已查證」的界線（重要）

**ODForge 目前不驗證內容的真偽。** 四道閘全綠的簡報，仍然可能包含：

- 模型捏造的統計數字、日期或引言；
- 指向不存在頁面的來源連結；
- 與使用者提供的參考文件不符的敘述。

現有的防線只有 prompt 層面的約束（「原始需求沒有提供的數字不要自行捏造」），而
**prompt 約束不是檢查**。系統性的內容查證需要 evidence provenance 與 citation
verification 流程，目前不在範圍內。

因此：

- 介面、CLI 報告與 README 都必須明說第四道閘檢查的是**版面設計**，不是事實。
- `Slide.sources` 的 `url` 只驗證格式（必須是 http(s)），**不驗證可存取性、標題
  或與內文的關聯**，一律視為「未查證」。
- 任何「內容可信」的宣稱，在查證流程實作之前都不得出現在產品文案裡。

## 五、文件型別支援範圍（定案）

| 介面 | .odp 簡報 | .odt 文件 | .ods 試算表 |
| ------ | ----------- | ----------- | ------------- |
| 核心引擎 | ✅ | ✅ | ✅ |
| CLI `odforge new` | ✅ | ✅ | ✅ |
| MCP `forge_*` | ✅ | ✅ | ✅ |
| **Web 控制台** | ✅ | ❌ | ❌ |

**Web 控制台專注 ODP，這是定案，不是待辦。** 理由：整個控制台的資訊架構建立在
「一頁＝一個可預覽、可單獨重生的單元」之上——縮圖牆、單頁 lightbox、逐頁 QA
findings、單頁重生，全部依賴這個模型。文件與試算表沒有「頁」這個天然單元
（.odt 的分頁由算圖決定，.ods 是工作表與儲存格），直接套用簡報的假設會做出一個
每一格都在說謊的介面。

`POST /api/generate` 對 `doc_type != "odp"` 回 **422** 並附中文說明，而不是靜默
接受再交付一份 `.odp`。前端只顯示 ODP 一種格式，不擺放點了會失望的分頁。

若未來要接入，先決條件是：為每種文件型別各自定義預覽單元、QA 檢查項與重生語意，
而不是複用 slide 的假設。
